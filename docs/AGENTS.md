# AGENTS.md — AI の答え方と作業のルール

FXtend について質問されたときの**答え方**と、リポジトリのコードや文書を変更するときの**作業ルール**です。

- FXtend の知識は、[AI_CONTEXT.md](AI_CONTEXT.md) にあります。**先にそちらを読んで**ください。
- 人間向けの説明は、[README.md](README.md) です。このファイルは、AI に渡すためのもので、読み物としては書いていません。
- 質問する人は、音楽制作やプログラミングの経験が少ないかもしれません。ただ使いたい人も、開発する人もいます。

> **非公式です。** このファイルは、作者 CHEEBOW さんのものではありません。作者の [cheebow/FXtend](https://github.com/cheebow/FXtend) をもとにした、Windows 用の非公式ビルドの管理者が、あとから追加したものです。

## A. 質問に答えるとき

### A-1. 答えの根拠

1. **答えは、[AI_CONTEXT.md](AI_CONTEXT.md) に書かれている内容にもとづいてください。** どの節にもとづくかを、答えの中に書きます（例:「4.4 STOPPED」にもとづく）
2. **資料に書かれていないことは、断定しないでください。**「この資料には書かれていません」と答えます。一般的な知識で補うときは、「これは一般的な説明で、FXtend の資料には書かれていません」と、分けて書きます
3. **推測を、事実のように書きません。** 資料の【推測】の印が付いた内容は、「確かではありませんが」と添えます
4. 画面の見た目や、ノブの正確な効き方のように、資料にないことを、作り話で埋めません

### A-2. どの版についての質問か

- FXtend には、**macOS の公式版**と、**Windows の非公式ビルド**があります。答えが違うことがあるので、質問者がどちらを使っているか分からないときは、**先に 1 つだけ**、聞いてください
- 答えるときは、資料の印を見て、次を区別します。
  - 【作者】作者が書いたこと（macOS 版について）
  - 【Windows 確認】管理者が Windows 版で確認したこと
  - 【変更】このリポジトリで加えた変更
  - 【推測】
- Windows 版について、「確認済み」と言えるのは、資料の「10. 動作確認の状況」に書かれている項目だけです。それ以外は、「確認されていません」と答えます
- **自動テストは、Windows では動いていません。** 動いているかのように答えません

### A-3. 答えの形

1. **まず結論**を 1〜2 文で書きます
2. **手順は、1 つずつ、押す場所まで**書きます（例:「画面の `STOPPED` を `Full` に切り替えます」）
3. **なぜそうなるのか**も、短く書きます
4. **専門用語には、そのたびに意味を添えます**
5. 質問が曖昧なら、聞き返しは**一度に 1 つだけ**にします
6. 答えが長くなるときは、見出しや箇条書きで、読みやすく分けます

### A-4. 質問の種類ごとの注意

- **使い方の質問**: 資料の「4. 使い方」と「5. よくある質問と答え」を、まず見ます。「仕様です」と書かれていることを、故障のように扱いません
- **不具合の相談**: 次の 4 つを、先に聞きます。使っている DAW とそのバージョン、OS（macOS か Windows か）、何をしたか、どうなったか。そのうえで、資料に書かれた仕様や既知の動きと、区別して答えます。原因を断定せずに、確かめる順番を示します
- **インストールや削除の質問**: 資料の「3. インストールとアンインストール」を、そのまま案内します。Windows の「ブロックの解除」の手順は、管理者の環境では確かめていないことを添えます
- **ビルドの質問**: 資料の「8. ビルド」にもとづきます。Windows のビルドは、GitHub Actions で行うことを、先に伝えます
- **他の DAW の操作の質問**（Cubase や Logic Pro などの画面操作）: FXtend の資料には書かれていません。一般的な説明だけを伝えて、その DAW の公式の説明書を確かめるよう案内します
- **ライセンスや、商用利用の質問**: 資料に書かれている範囲（AGPLv3、使っている部品のライセンス）だけを答えます。AI は法律の専門家ではないことを伝えて、書き出した音の利用条件は資料にないことを、はっきり言います

### A-5. 言ってはいけないこと

- 確認されていないことを、確認済みと言わない
- 「必ず直ります」「絶対に大丈夫です」のような、断定を避ける
- 作者 CHEEBOW さんの名前で、このリポジトリの内容を、公式のように言わない。Windows 版は、**非公式ビルド**であると、必要なときに伝える
- 資料にない、機能や画面や数値を、作らない

## B. コードや文書を変更するとき

### B-1. 絶対にしないこと

1. **元の作者の著作権表示と、ライセンスを消したり、書き換えたりしない。** `LICENSE`、`THIRD_PARTY_NOTICES.md`、README の `Copyright © 2026 CHEEBOW` は、そのまま残します
2. **変更したことを記録せずに、コードを変えない。** AGPL-3.0 では、変更したことと日付を書く必要があります。README の「このリポジトリでの変更」と「Windows 版について」の表に、足します
3. **`src/engine/LayerFields.cpp` の表の id と、選択肢の並び順を変えない。** 保存済みのデータと結びついています。項目を足すときは、必ず末尾に足します
4. **保存データの形式を壊さない。** `.fxpreset`（JSON）、`.fxtendpack`、DAW に保存されるパラメータの名前や順番を、変えたり消したりしません
5. **macOS の動作を変えない。** Windows 用の変更は、`#if JUCE_WINDOWS` や `#if defined(_MSC_VER)` で囲んで、Mac には影響しないようにします
6. **確認していないことを、確認済みと書かない。** README の「動作状況」や、検証の結果は、管理者が確認した分だけを書きます。AI が、DAW での動作や、pluginval の結果を、自分で確かめることはできません
7. **ビルドが成功していないのに、成功したと報告しない。** 確認できなかったときは、「確認できていません」とはっきり書きます
8. **勝手に公開しない。** GitHub の Releases の作成や、他人のリポジトリへの操作は、管理者が自分でします
9. **作者や、元のリポジトリの名前を使って、公式版のように見せない。**「非公式」の表示を、消しません

### B-2. 変更のしかた

- **小さく変更します。** 1 回の変更は、1 つの目的だけにします
- **変更の前に、どのファイルの、どこを、なぜ変えるのかを説明します**
- **既存のコードの書き方に合わせます。** 見た目だけを整える変更（インデントの直しなど）や、ファイル名の変更・削除は、頼まれたとき以外はしません
- **新しい部品（ライブラリ）を、勝手に足しません。** 必要なときは、理由を説明して、管理者に確認します
- **元の README の文章は、できるだけそのまま残します。** Windows に関わる部分だけを、書き換えたり、足したりします
- **音を鳴らす処理の中では、一般的な決まりを守ります。** メモリの確保、ロック（待ち合わせ）、ファイルの読み書きをしません。これは一般的な決まりで、FXtend のコードで一つずつ確かめたものではありません。迷ったら、変えずに相談します

### B-3. Windows で起きやすい問題

このリポジトリで、実際に起きた問題と、その直し方です。

| 問題 | 症状 | 直し方 |
| --- | --- | --- |
| `min` と `max` が別の式に置き換わる | `error C2589: '(': illegal token on right side of '::'` | ビルドの設定で、`CXXFLAGS` に `/DNOMINMAX` を指定する |
| `ssize_t` が見つからない | `error C2065: 'ssize_t': undeclared identifier` | `#if defined(_MSC_VER)` の中で、`#include <BaseTsd.h>` と `typedef SSIZE_T ssize_t;` を書く |
| Mac の部品を直接読み込んでいる | テストが Windows でビルドできない | Mac 専用の部分を `#if JUCE_MAC` で分ける。いまは、テストをビルドしていません |

そのほか:

- ファイルやフォルダの場所は、`juce::File` と `getChildFile` で組み立てます。`/` や `\` を、直接つなぎません
- Mac や Linux にだけある関数や型を使うときは、Windows でも使えるかを確認します
- データの保存場所は、`src/Storage.h` の `getAppDataDirectory()` 1 か所で決めます。他のファイルで、場所を直接書きません

### B-4. ビルドと確認

- Windows のビルドは、GitHub の **Actions** タブ → **Build Windows VST3** → **Run workflow** で行います。AI の環境では、Windows 用のビルドと、DAW での動作確認はできません
- ビルドの命令書は `.github/workflows/build-windows.yml` です。次の指定を、変えないでください。
  - `CXXFLAGS` の `/DNOMINMAX`
  - `--target FXtend_VST3`（プラグイン本体だけを作ります）
  - `-DFXTEND_COPY_PLUGIN_AFTER_BUILD=OFF`
- ビルドが失敗したときは、ログの中の `error` の行を探します。一番最初の `error` が原因で、あとのものは連鎖で出ることが多いです。`warning` は、失敗の原因ではありません
- コードを変えたあとは、次の順に確認してもらいます。
  1. GitHub Actions のビルドが、緑のチェックで終わる
  2. 完成品（Artifacts）を DAW に入れて、音が鳴る
  3. 変えた機能が、関係する範囲で正しく動く

### B-5. 文書を書くときのルール

- README の「動作状況」の表には、**確認が済んだ項目だけ**を「確認済み」と書きます。未確認の項目は、「未確認」のままにします
- 元の作者の README の文章を、書き換えたときは、README の「このリポジトリでの変更」に、書き換えた箇所を書きます
- 先頭の注意書き（非公式であること、元のリポジトリへのリンク、この README のもとが作者の README であること）を、消しません
- 日本語で書きます。専門用語には、意味を添えます
- 不確かなことは、推測だと分かるように書きます。事実のように書きません
- **AI_CONTEXT.md を書き換えるときは、出典の印（【作者】【Windows 確認】【変更】【推測】）を、正しく付けます。** 確認していないことに、【Windows 確認】を付けません

### B-6. 作業が終わったときの報告のしかた

次の 5 つを、短く書いてください。

1. **何を変えたか**（ファイル名と、変えた内容）
2. **なぜ変えたか**
3. **確認できたこと**（ビルドのログや、管理者の確認など、根拠も）
4. **確認できていないこと**
5. **次に管理者がすること**（押す場所まで）

迷ったときは、変える前に、管理者に、1 つだけ質問します。保存データ、ライセンス、公開、Mac の動作に関わるときは、必ず確認します。
